## 二、先补的共用能力（核心库和服务端）

原则：**规则只在核心库写一份；网页和安卓只渲染，"要填什么、能选什么、结论是什么"都由服务端调核心算出来**。网页不自己拼 segments、不自己挑条件、不自己定测试项。

### 2.1 建档：`recommendProduct`、`conditionsFor`、`choiceGroups`（P0-1、P0-2、P0-8）

- **`recommendProduct(manifest, rules, answers)`**：按入口问卷 Q1（学段）、Q3（场地，只问 18–64 岁）推出起始期成品。
  - 学龄前、孕期、产后 6 个月内返回"不覆盖"和原因；
  - 附册、稳定期成品不进可选列表；
  - 同时按 rules 登记的"直接进入"门槛（`cli.ts:96–98` 读的有基础每周力量天数、俯卧撑级、次数）告诉网页：这份成品能不能走"有基础、直接进稳定期"，门槛是多少。
- **`conditionsFor(rules, product, screening)`**：只返回 `rules.conditions` 里 `products` 含这份成品的项。
  - 每项带 `ask`、`note`、`per_session`；
  - 有依赖的项按筛查答案决定问不问：如"重度肥胖"只在筛查"BMI ≥ 28"答"是"、并且是徒手或居家版时问；"有氧问过医生"只在有高血压或重度肥胖时问；
  - 问法用 rules 原话，不改成否定问句。
- **`choiceGroups(plans, product, conditions)`**：训练单里 `trim.kind === "choose"` 的行，按 `condition` 分组，返回 `{ condition?: {name, value}, options: { id?: string; text: string }[] }[]`。
  - "（门框划船）"这种不是动作 ID 的选项照原文作为文字选项，`id` 空；
  - 网页**先问条件、再问器材**（器材随条件答案变），可以多选、排先后（`choices` 按优先顺序记，照 onboard skill 第 8 步）。
- **基本信息按年龄段**：
  - 18–64 岁：问体重腰围"记 / 不记"（`body`），不预选；
  - 65 岁以上：问建档时的散步分钟（`habitBase`），不预填；
  - 6–17 岁：问学段、入学年份和 `school.system`；
  - 出生年月不预填。
- **直接进稳定期（P0-8）**：见决定 5。建议把入门评估并进建档向导最后一步（`createProfileOp` 已支持 `initialAssessment`）：有基础的人在这一步填训练基础、俯卧撑测试，选方向（focus）。
- **放行条件**：`profile-ops.ts:293` 的放行改成按 `code` 判断（见 2.5），不再按报错文字过滤。

### 2.2 评估表单：`assessmentForm`（P0-3）

把 `cli.ts` 列项那段（394–473）下沉到 `assess.ts`，返回结构化表单。**每项怎么填，由 rules 的 `fields` 加核心枚举推出来，不另写一套输入类型**。

```ts
interface AssessmentForm {
  kind: "入门" | "段末" | "周期末" | "触发";
  product: string;                    // 跨段、换场地：可换的新成品列表 + 新成品的入门项
  segment?: number;                   // 段末、周期末由服务端填好
  notes: string[];                    // 如"65 岁以上的测试在医生同意以后、家人在场时做"
  prereqs: Field[];                   // 开工前提
  base?: Field;                       // 训练基础（入门；18–64、13–17）
  focus?: Field;                      // 方向（有基础、直接进稳定期的人）
  tests: TestField[];                 // 由 rules.assess 的测试和 fields 推出；俯卧撑级名取 plans.json ladders；
                                      // 静蹲带高血压上限；gym-weights 从个人进度带入、只读
  body?: Field[];                     // 18–64 岁且 body = "记"
  fallRisk?: FallRiskForm;            // 65 岁以上自查（照 3c 结构）
  top: Field[];                       // TOP_KEYS 里这一种评估、这个人要填的：eventDate(s)、doctorCleared/doctorDate、
                                      // doctorRestart、companion、fallAssessDone、weightDrop、goal/eatingCheck/goalConsent（只限 18–64）、
                                      // official/fallRiskSeen 等
  reasons?: string[];                 // 触发：取 REASONS，不另写
  endSummary?: EndSummary;            // 段末、周期末：已有的 inspectEndSummary
}
// Field 带 key、问法原文、取值（枚举 / 整数范围 / 日期 / 是否）、是否必填、依据原文
```

- **命令行**：`course assess` 改成打印这份结构，输出逐字不变。改动前先给各成品、各种评估留输出快照，改完逐字比对。
- **服务端**：`GET /api/profiles/:id/assessments/form?kind=…[&reason=…&product=…]`，网页按 Field 渲染。遇到不认识的取值类型时，网页显示"这一项网页还不支持，请用命令行"，不静默丢掉。
- **结论**：照旧由 `evaluateAssessment` 重算。服务端出 `presentConclusion`，把结论翻成人话（"可以进稳定期""下一段：减量段，散步目标降到……"），不显示原始 JSON。
- **本轮不做"培训"**：评估种类里的"培训"（模板 v1.0.0 的 `rules.assess.mastery`）本轮不做，表单遇到时照上面的方式提示。

### 2.3 周复盘：`reviewForm` 和服务端拼下一周（P0-4）

`reviewForm(bundle, rules, week)` 返回这一周要填的项：

- **训练次数**：从这一周的练习记录数带入，只能改大。
- **不适**：有不适的记录就自动勾上，不能取消。
- **半量**：`half` 从记录带入。
- **每个动作的依据**（`moves`）：从记录里的 `perItem` 汇总（感受、还能做几下、退回），可以补。
- **稳态自查**（`steadyCheck`）：轮到稳态自查的周才出现。
- **习惯项**：取 `rules.habits` 按成品、段型、周筛出来的那几项——这是段末要考核的打卡项，不是每天 3 到 7 项的全部，界面照这个说明；按现有 review/1 填 0–7（见决定 6）。
- **按年龄段**：65 岁以上填 falls、nearFalls、dizzy；6–12 岁填 sickDays。
- **减脂的人**：填每周复盘的那几项。体重只在 body = "记"时出现，一周最多一次；另有有氧分钟、练完有没有没力气。
- **正文**：只预放声明一行。

**下一周怎么走**由服务端给可选项：推到下一周 / 这一周重来 / 段末评估。有不适不能推周。下一周的 segments 项**由服务端算**，网页只传选了哪项。

**提交时**服务端对这一周单独核对：训练次数不少于记录数、不适和记录一致。这里不依赖 `checkProgress`，因为它会跳过最后一项。

### 2.4 个人进度入口（P0-7）

- **一份写法**：把 `update_progress_log` 的写法提到 `profile-ops.ts`（`appendProgressLogOp`），Agent 工具和网页共用；写入后照旧重放核对，不合规则的拒；下调进度时作废过重的旧课。
- **网页入口**：复盘页加"个人进度"一步：
  - 列出每个有个人进度的动作：现在的级 / 次数 / 重量，加上这一周的依据（2.3 的 `moves`）；
  - 使用者填改成多少、依据哪条规则（从成品的进度规则里选，不手写），或者"不改"；
  - 提交后服务端重放核对。
- **网页不推荐**：改不改由使用者照成品规则决定，网页不替他推荐。

### 2.5 给人看的报错（P1-11）

- `Issue` 加可选的 `code`（如 `ENTRY_ASSESSMENT_MISSING`、`STAGE_INVALID`）。核心库里提到文件名、命令的那批报错补上 `code`，文案不动，命令行照旧。
- 服务端出 `presentIssue(issue)`：
  - 有 `code` 的换成网页说法，如"第一段开始之前要先做入门评估"；
  - 没有 `code` 的去掉"档案.json""npm run …"这类字样；
  - 返回给网页的 `issues` 都要经过它。

### 2.6 接口类型共用（P1-9）

- 服务端把请求、返回的 zod 结构集中到 `apps/server/src/api/contracts.ts`，导出类型。
- 处理函数的返回值用 `satisfies` 对上这些类型，这样服务端改了字段，类型检查就报错。
- 网页用 `import type` 引用（只引类型，不打包服务端代码），删掉自己另写的那份。

### 2.7 时间轴事件带显示用的结构化字段（P1-10）

在 `TimelineEvent` 上加只读的 `view`，由 `timeline.ts` 生成时写入，不改现有字段：

```ts
view: {
  breath: "inhale" | "exhale" | null;   // 和 breathPluck.direction 同一来源；没有 pluck 的拍也写
  tempo: "down" | "up" | "top" | "bottom" | null;
  rep: { n: number; of: number } | null;
  secLeft: number | null;               // 计时动作、休息的倒数
  restTotal: number | null;             // 这段休息一共几秒
  side: "左侧" | "右侧" | null;
  sideSwitch: boolean;
  done: boolean;                        // 计时做完那一拍
}
```

- **改读 `view`**：`live-view.ts` 和安卓 `LiveViewMath.kt` 都改读 `view`。显示状态、数字、倒数一律来自字段，不再正则解析显示文字；只给人看的文字整理（`stripLead` 去掉前面的图标）可以保留。
- **对 v1 没有影响**：原版比对只比 t、cue、voice、state、final（`original.test.ts:89`），导出快照不含时间轴。
- **黄金测试集**：重新生成，另加 `view` 的用例。
- **重打包**：F1 改完核心，要重打包 `player-runtime.js` 并复制到安卓 assets，因为安卓构建会校验两份字节一致（`build.gradle.kts:65–93`）。

### 2.8 初始化保护和健康检查（P1-12）

## 四、隐私和安全

- **不新增要记的个人数据**，范围照 AGENTS.md：
  - 筛查只记是 / 否；
  - 条件只记是 / 否，没确认的不写；
  - 体重腰围要选"记"才记；
  - 65 岁以上自查只记答案和秒数；
  - 进食困扰那一问只记"问过"或"只能保持"。
- **"重度肥胖"**：身高体重只在浏览器里当场算，不提交、不进日志。
- **网页表单里的高敏项**（体重腰围、进食困扰、重度肥胖）：照架构方案 4.3，不经过大模型。
- **13–17 岁、6–12 岁的页面**：不出现体重、热量、减肥字样；网页 e2e 对这两个年龄段的页面加断言。
- **初始化口令**：只写本机日志和数据目录里权限 600 的文件，不进数据库、不进备份，用过即删。
- **安卓完成组数**：只认实际播放过的（决定 8 选 A 时），手动改不出"练过"。
